# 3.6. Caso N:M con atributos: entidad asociativa

> **Duración estimada:** 25 min (7 min teoría + 18 min práctica)

---

## 🧠 Teoría rápida (7 min)

En 3.4 modelamos Pizza ↔ Ingrediente como un `@ManyToMany` "plano": una tabla intermedia con solo dos FKs.

Pero **el negocio cambia constantemente** y, antes o después, alguien pregunta:
> "¿Y si una pizza puede tener 50g de mozzarella y 100g de salami? Necesitamos guardar **cantidades**."

La pregunta es simple. La consecuencia es enorme: la relación **deja de ser N:M plana**.

### Por qué el `@ManyToMany` ya no vale

Cuando solo había `pizza_id` y `ingrediente_id`, la tabla intermedia era un **detalle de implementación**. Hibernate la gestionaba sola.

Pero si añadimos `cantidad`, esa tabla deja de ser un detalle: **es una entidad con datos propios**. Y eso significa:
- Tiene su propia identidad (un `id`).
- Puede tener su propio ciclo de vida (¿se borra cuando se borra la pizza? sí. Cuando se borra el ingrediente? no debería).
- Puede tener métodos de negocio (`reducirCantidad`, `cambiarUnidad`…).

> 🔑 **Patrón canónico**: cuando una relación N:M gana atributos, **se promueve a entidad asociativa** (también llamada *join entity*).

### Cómo se modela en JPA

Adiós al `@ManyToMany`. Hola a **dos `@OneToMany`/`@ManyToOne`** que pasan por la nueva entidad:

```
Pizza  1 ──N  PizzaIngrediente  N ──1  Ingrediente
                  (cantidad, unidad…)
```

```sql
create table pizza_ingrediente (
    id              uuid primary key,
    pizza_id        uuid not null,
    ingrediente_id  uuid not null,
    cantidad        numeric(10,2) not null,
    unidad          varchar(20) not null,
    foreign key (pizza_id)       references pizzas (id),
    foreign key (ingrediente_id) references ingredientes (id),
    unique (pizza_id, ingrediente_id)  -- evita duplicar el mismo ingrediente en la misma pizza
);
```

### El dilema del cascade en este patrón

Si el lado `PizzaJpa` tiene `@OneToMany<PizzaIngredienteJpa>`, las preguntas obligatorias:

- **Al persistir Pizza**, ¿se persisten los `PizzaIngrediente` nuevos? → `CascadeType.PERSIST`. Sí.
- **Al borrar Pizza**, ¿se borran sus `PizzaIngrediente`? → `CascadeType.REMOVE` + `orphanRemoval = true`. Sí.
- **Al borrar un `PizzaIngrediente`**, ¿se borra el `Ingrediente`? → ¡NO! El ingrediente lo usan otras pizzas. **Sin cascade en ese lado.**

> ⚠️ **`orphanRemoval = true`** es distinto de `CascadeType.REMOVE`. El primero borra hijos cuando los **quitas de la colección** del padre (aunque el padre no se borre). El segundo borra hijos solo cuando se borra el padre.

### Cuándo NO promover

Promover una N:M a entidad asociativa **es coste**: una tabla más, un mapper más, decisiones de cascade. **No lo hagas si no aporta**.

- ¿Solo necesitas saber "qué ingredientes lleva esta pizza"? `@ManyToMany` plano basta.
- ¿Necesitas guardar gramos, unidades, orden de capas, fecha de incorporación, opcionalidad ("queso opcional")…? Promueve.

> **Heurística**: si la pregunta "¿qué columnas extra tendría la tabla intermedia?" devuelve cualquier respuesta que no sea "ninguna", promueve.

## 🛠 Práctica guiada (18 min)

Vamos a evolucionar nuestra relación Pizza-Ingrediente para soportar **cantidades**. Mantenemos lo que ya tenemos del 3.4 funcionando, así que partimos de ese punto.

### Paso 1 — Nuevo concepto en el dominio: `IngredienteEnPizza`

Antes de tocar nada de JPA, modelamos la idea en el dominio. Recuerda nuestra regla: **dominio primero**.

```java
package com.pizzeria.domain.pizza;

import com.pizzeria.domain.ingrediente.Ingrediente;
import com.pizzeria.domain.shared.Money;

import java.math.BigDecimal;
import java.util.Objects;

public final class IngredienteEnPizza {

    private final Ingrediente ingrediente;
    private final BigDecimal cantidad;     // por simplicidad: en gramos

    private IngredienteEnPizza(Ingrediente ingrediente, BigDecimal cantidad) {
        this.ingrediente = ingrediente;
        this.cantidad = cantidad;
    }

    public static IngredienteEnPizza of(Ingrediente ingrediente, BigDecimal cantidad) {
        Objects.requireNonNull(ingrediente, "ingrediente requerido");
        Objects.requireNonNull(cantidad, "cantidad requerida");
        if (cantidad.signum() <= 0) {
            throw new IllegalArgumentException("La cantidad debe ser positiva: " + cantidad);
        }
        return new IngredienteEnPizza(ingrediente, cantidad);
    }

    public Money costeParcial() {
        // coste del ingrediente × cantidad (asumimos coste por unidad de cantidad)
        BigDecimal total = ingrediente.coste().amount().multiply(cantidad);
        return new Money(total);
    }

    public Ingrediente ingrediente() { return ingrediente; }
    public BigDecimal cantidad() { return cantidad; }
}
```

> 🧠 **Decisiones a comentar:**
> - Es una clase final con factory `of()`: igual de inmutable que nuestros value objects. Pero **no es un value object puro** porque arrastra una entidad (`Ingrediente`). Es un patrón intermedio común.
> - Tiene un método de negocio (`costeParcial`) — es el motivo por el que existe esta clase, en vez de un simple `Map<Ingrediente, BigDecimal>`.
> - No tiene `id` propio. **En el dominio no lo necesita**. El id que aparecerá en JPA es un detalle de almacenamiento.

### Paso 2 — Refactor de `Pizza` en el dominio

```java
public class Pizza {
    private final PizzaId id;
    private String nombre;
    private List<IngredienteEnPizza> ingredientes;   // antes era List<Ingrediente>

    public static Pizza create(String nombre, List<IngredienteEnPizza> ingredientes) {
        if (ingredientes == null || ingredientes.isEmpty()) {
            throw new IllegalArgumentException("Una pizza necesita al menos un ingrediente");
        }
        return new Pizza(PizzaId.nuevo(), nombre, new ArrayList<>(ingredientes));
    }

    public static Pizza restore(PizzaId id, String nombre, List<IngredienteEnPizza> ingredientes) {
        return new Pizza(id, nombre, new ArrayList<>(ingredientes));
    }

    public Money precio() {
        BigDecimal subtotal = ingredientes.stream()
            .map(ip -> ip.costeParcial().amount())
            .reduce(BigDecimal.ZERO, BigDecimal::add);
        return new Money(subtotal.multiply(new BigDecimal("1.20")));
    }

    public List<IngredienteEnPizza> ingredientes() {
        return List.copyOf(ingredientes);
    }
    // ...
}
```

> ✅ Observa: la API pública de `Pizza` apenas cambia. El `precio()` sigue siendo "suma de ingredientes × 1.20", solo que ahora cada uno aporta `cantidad × coste`. **Esa es la prueba de un buen dominio**: el cambio se absorbe sin propagarse.

### Paso 3 — Nueva entidad JPA: `PizzaIngredienteJpa`

```java
package com.pizzeria.persistence.pizza;

import com.pizzeria.persistence.ingrediente.IngredienteJpa;
import jakarta.persistence.*;
import java.math.BigDecimal;
import java.util.UUID;

@Entity
@Table(
    name = "pizza_ingrediente",
    uniqueConstraints = @UniqueConstraint(columnNames = {"pizza_id", "ingrediente_id"})
)
public class PizzaIngredienteJpa {

    @Id
    @Column(name = "id", nullable = false, updatable = false)
    private UUID id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "pizza_id", referencedColumnName = "id", nullable = false)
    private PizzaJpa pizza;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "ingrediente_id", referencedColumnName = "id", nullable = false)
    private IngredienteJpa ingrediente;

    @Column(name = "cantidad", nullable = false, precision = 10, scale = 2)
    private BigDecimal cantidad;

    protected PizzaIngredienteJpa() {}

    public PizzaIngredienteJpa(PizzaJpa pizza, IngredienteJpa ingrediente, BigDecimal cantidad) {
        this.id = UUID.randomUUID();
        this.pizza = pizza;
        this.ingrediente = ingrediente;
        this.cantidad = cantidad;
    }

    public UUID getId() { return id; }
    public PizzaJpa getPizza() { return pizza; }
    public IngredienteJpa getIngrediente() { return ingrediente; }
    public BigDecimal getCantidad() { return cantidad; }
}
```

> 🔍 **Detalles:**
> - El `id` es un `UUID` simple. En el dominio no existe; aquí sí porque JPA lo necesita.
> - **Dos `@ManyToOne`**, ambos lazy, ambos `optional = false`.
> - El `@UniqueConstraint` en `@Table` evita que aparezca dos veces el mismo `(pizza_id, ingrediente_id)`.

### Paso 4 — Modificar `PizzaJpa` para usar la nueva entidad

```java
@Entity
@Table(name = "pizzas")
public class PizzaJpa {

    @EmbeddedId
    @AttributeOverride(name = "value", column = @Column(name = "id", nullable = false, updatable = false))
    private PizzaId id;

    @Column(name = "nombre", nullable = false, length = 100, unique = true)
    private String nombre;

    @OneToMany(
        mappedBy = "pizza",
        cascade = { CascadeType.PERSIST, CascadeType.MERGE, CascadeType.REMOVE },
        orphanRemoval = true,
        fetch = FetchType.LAZY
    )
    private List<PizzaIngredienteJpa> items = new ArrayList<>();

    protected PizzaJpa() {}

    public PizzaJpa(PizzaId id, String nombre) {
        this.id = id;
        this.nombre = nombre;
    }

    public void addItem(PizzaIngredienteJpa item) {
        items.add(item);
    }

    public PizzaId getId() { return id; }
    public String getNombre() { return nombre; }
    public List<PizzaIngredienteJpa> getItems() { return items; }
}
```

> 🔑 **Cascade en este caso, explicado:**
> - `PERSIST` → al persistir la pizza, sus `PizzaIngredienteJpa` se persisten también. Cómodo: ahorras tener que persistir item por item.
> - `MERGE` → si actualizamos la pizza (otra cantidad, nuevo item), los cambios se propagan.
> - `REMOVE` → si borramos la pizza, se borran sus items. ✅
> - `orphanRemoval = true` → si quitamos un item de `items` (`items.remove(...)`), se borra esa fila. Sin esto, quedaría huérfana.
> - **NUNCA `CascadeType.ALL`** aquí, porque arrastraría el borrado al `IngredienteJpa` referenciado, y eso es un agregado distinto.

### Paso 5 — Mapper completo

```java
package com.pizzeria.persistence.pizza;

import com.pizzeria.domain.pizza.IngredienteEnPizza;
import com.pizzeria.domain.pizza.Pizza;
import com.pizzeria.persistence.ingrediente.IngredienteJpa;
import com.pizzeria.persistence.ingrediente.IngredienteMapper;
import jakarta.persistence.EntityManager;

public class PizzaMapper {

    private final IngredienteMapper ingredienteMapper;

    public PizzaMapper(IngredienteMapper ingredienteMapper) {
        this.ingredienteMapper = ingredienteMapper;
    }

    public PizzaJpa toJpa(Pizza pizza, EntityManager em) {
        PizzaJpa jpa = new PizzaJpa(pizza.id(), pizza.nombre());

        for (IngredienteEnPizza ip : pizza.ingredientes()) {
            // Reutilizamos el IngredienteJpa de la sesión, no creamos uno nuevo
            IngredienteJpa ingJpa = em.getReference(IngredienteJpa.class, ip.ingrediente().id());

            PizzaIngredienteJpa item = new PizzaIngredienteJpa(jpa, ingJpa, ip.cantidad());
            jpa.addItem(item);
        }
        return jpa;
    }

    public Pizza toDomain(PizzaJpa jpa) {
        var ingredientes = jpa.getItems().stream()
            .map(item -> IngredienteEnPizza.of(
                ingredienteMapper.toDomain(item.getIngrediente()),
                item.getCantidad()
            ))
            .toList();
        return Pizza.restore(jpa.getId(), jpa.getNombre(), ingredientes);
    }
}
```

> 🚨 **Por qué `em.getReference`** y no `em.find`: solo necesitamos enlazar la FK; no queremos un `SELECT` extra a la tabla `ingredientes` por cada item. `getReference` devuelve un proxy con solo el id; basta.

### Paso 6 — Verificar el DDL

Lanza otra vez `Main`. Esperado:

```sql
create table pizza_ingrediente (
    id              uuid not null primary key,
    cantidad        numeric(10,2) not null,
    ingrediente_id  uuid not null,
    pizza_id        uuid not null,
    constraint pizza_ingrediente_unique unique (pizza_id, ingrediente_id),
    constraint FK_pi_pizza       foreign key (pizza_id) references pizzas,
    constraint FK_pi_ingrediente foreign key (ingrediente_id) references ingredientes
)
```

Comparación con 3.4: ahora la tabla intermedia es una **entidad de pleno derecho** con `id` propio y la columna `cantidad`.

## 🎯 Cierre

- N:M con atributos → entidad asociativa. **No hay alternativa razonable**.
- Adiós `@ManyToMany`, hola dos `@ManyToOne` y un `@OneToMany` con cascade fino.
- `orphanRemoval` ≠ `CascadeType.REMOVE`. Sutil pero importante.
- **Nuestro dominio acompaña el cambio sin romperse**, porque tenía buena forma de entrada.

En **3.7** salimos del agregado `Pizza` y tratamos el `@OneToOne` Comment→User. Es un caso interesante porque está **mismodelado a propósito** para que veamos qué problemas surgen y cómo se detectan.
