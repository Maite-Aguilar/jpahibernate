# 3.7. Caso `@OneToOne` Comment→User: implicaciones de índices y queries

> **Duración estimada:** 25 min (8 min teoría + 17 min práctica)

---

## 🧠 Teoría rápida (8 min)

Hoy hacemos algo poco habitual en un curso: **vamos a modelar mal a propósito** para ver cómo se detectan los errores. Específicamente, vamos a defender la idea de que `Comment` y `User` están relacionados como `@OneToOne` y ver hasta dónde llega esa decisión antes de descubrir el problema.

### Cuándo SÍ tiene sentido `@OneToOne`

Una relación 1:1 en la realidad significa **"para cada A hay como mucho un B, y para cada B como mucho un A"**.

Ejemplos legítimos:
- `User` ↔ `UserProfile` (datos extendidos del usuario).
- `Pedido` ↔ `Factura` (cada pedido genera exactamente una factura).
- `Empleado` ↔ `Despacho` (asumiendo que cada empleado tiene un único despacho y al revés).

En todos esos casos, el 1:1 **es** la relación.

### Cuándo NO tiene sentido (nuestro caso)

`Comment` y `User` **no son 1:1**. Un usuario puede dejar **muchos** comentarios. La relación correcta es:

- Desde `Comment`: `@ManyToOne` a `User` (lo que ya hicimos en 3.5).
- Desde `User`: `@OneToMany` a `Comment` (si la quisiéramos bidireccional).

Aun así, este caso aparece en proyectos reales más de lo que parece. Las dos razones típicas:

1. **Malentendido del negocio.** Alguien lee "cada comentario tiene un autor" y traduce a `@OneToOne` porque "tiene **uno**". Confunde la cardinalidad del lado con la cardinalidad de la relación.
2. **Copy-paste sin pensar.** Vieron `@OneToOne` en un tutorial para `User-UserProfile` y lo aplicaron donde no toca.

### Qué pasa si modelamos `Comment @OneToOne User`

Hibernate hará lo siguiente:

```sql
create table comments (
    id      uuid not null primary key,
    texto   varchar(1000) not null,
    user_id uuid not null,
    constraint UK_comments_user unique (user_id),  -- ¡UNIQUE!
    foreign key (user_id) references users (id)
);
```

Sí: `@OneToOne` con FK en `comments` añade un **constraint `UNIQUE`** a `user_id`. Eso significa que **un usuario solo puede tener un comentario**. En cuanto intentes insertar el segundo:

```
ConstraintViolationException: Unique index or primary key violation:
"UK_comments_user_id ON PUBLIC.COMMENTS(USER_ID)"
```

> 🎯 **Síntoma → diagnóstico**: si ves un `UNIQUE` violado en una columna FK donde **esperarías muchas filas con el mismo valor**, la relación está mismodelada como 1:1.

### Tres lecciones a extraer del fallo

Aunque el modelo es incorrecto, su autopsia enseña tres cosas valiosísimas:

#### Lección 1 — `@OneToOne` genera índices `UNIQUE`

Esto **es bueno** cuando la relación realmente es 1:1: te garantiza la cardinalidad a nivel de BD. Y **es malo** cuando no lo es: te bloquea inserciones legítimas.

#### Lección 2 — Defaults `EAGER` del `@OneToOne`

Como vimos en 3.4, `@OneToOne` carga **EAGER por defecto**. Si modelamos mal y además dejamos el default:

```java
@OneToOne  // ← EAGER por defecto
private UserJpa autor;
```

Cada vez que cargas un comentario, **se carga también el usuario**. Listar 100 comentarios → 100 SELECTs adicionales a `users`, uno por comentario. Bienvenido al **problema N+1**.

#### Lección 3 — El problema N+1, visto desde el código

El N+1 ya lo hemos mencionado. Aquí lo **vamos a provocar** para que los alumnos lo vean en consola:

```java
List<CommentJpa> comments = em.createQuery(
    "SELECT c FROM CommentJpa c", CommentJpa.class).getResultList();

for (CommentJpa c : comments) {
    c.getAutor().getNombre();  // EAGER ya lo cargó; LAZY lo cargaría aquí
}
```

Con `EAGER`: **1 query** para la lista + **N queries** para cada autor = N+1 SELECTs.
Con `LAZY`: **1 query** para la lista, y luego **N queries** al acceder `getAutor()` en el bucle = el mismo problema.

¿Solución? Cargar todo de una con `JOIN FETCH` (Bloque 5):
```sql
SELECT c FROM CommentJpa c JOIN FETCH c.autor
```

Una sola query.

> 💡 El N+1 **no lo causa LAZY**. Lo causa **acceder a los hijos en bucle sin haberlos pedido junto al padre**. EAGER lo "esconde" porque al menos ocurre todo de golpe al cargar, pero el problema sigue ahí.

## 🛠 Práctica guiada (17 min)

Vamos a hacer el ejercicio de modelar `Comment @OneToOne User` y romperlo deliberadamente. Después corregimos.

### Paso 1 — Modificar `CommentJpa` para usar `@OneToOne` (mal modelado)

Toma el `CommentJpa` del 3.5 y cambia la anotación:

```java
@Entity
@Table(name = "comments")
public class CommentJpa {

    @EmbeddedId
    @AttributeOverride(name = "value", column = @Column(name = "id", nullable = false, updatable = false))
    private CommentId id;

    // ❌ MAL MODELADO — A PROPÓSITO
    @OneToOne(optional = false)               // ← antes era @ManyToOne(fetch = LAZY)
    @JoinColumn(name = "user_id", referencedColumnName = "id", nullable = false)
    private UserJpa autor;

    @Embedded
    @AttributeOverride(name = "value", column = @Column(name = "pizza_id", nullable = false, updatable = false))
    private PizzaId pizzaId;

    @Column(name = "texto", nullable = false, length = 1000)
    private String texto;

    @Embedded
    @AttributeOverride(name = "value", column = @Column(name = "fecha", nullable = false, updatable = false))
    private FechaComentario fecha;

    // resto igual...
}
```

> 💡 Nota: hemos quitado el `fetch = LAZY` explícito para que tome el default `EAGER` de `@OneToOne`. Queremos ver el N+1 oculto.

### Paso 2 — Lanzar y mirar el DDL

Ejecuta `Main` con `hibernate.hbm2ddl.auto=create`. Observa la consola:

```sql
create table comments (
    id        uuid not null primary key,
    fecha     timestamp not null,
    pizza_id  uuid not null,
    texto     varchar(1000) not null,
    user_id   uuid not null,
    constraint UK_comments_user_id unique (user_id),    -- ⚠️ AHÍ ESTÁ
    constraint FK_comments_user foreign key (user_id) references users
)
```

✅ El `UNIQUE` salta. La BD nos está avisando: "para mí, un usuario solo puede tener un comentario".

### Paso 3 — Provocar el error de `UNIQUE`

Crea un test rápido en `Main`:

```java
public static void main(String[] args) {
    EntityManagerFactory emf = Persistence.createEntityManagerFactory("pizzeriaPU");
    EntityManager em = emf.createEntityManager();

    em.getTransaction().begin();

    UserJpa pedro = new UserJpa(UserId.nuevo(), "pedro@x.com", "Pedro");
    em.persist(pedro);

    // Primer comentario: OK
    CommentJpa c1 = new CommentJpa(
        CommentId.nuevo(), pedro, PizzaId.nuevo(),
        "Buenísima!", FechaComentario.ahora()
    );
    em.persist(c1);

    // Segundo comentario del MISMO usuario: petará
    CommentJpa c2 = new CommentJpa(
        CommentId.nuevo(), pedro, PizzaId.nuevo(),
        "Otra vez, brutal.", FechaComentario.ahora()
    );
    em.persist(c2);

    em.getTransaction().commit();
}
```

Resultado esperado en consola:

```
org.hibernate.exception.ConstraintViolationException:
could not execute statement [Unique index or primary key violation:
"PUBLIC.UK_COMMENTS_USER_ID ... ON PUBLIC.COMMENTS(USER_ID) VALUES (...)"]
```

> 🎯 **Aquí es donde se ve la lección**: el error no es del código Java —compila bien—. Es **del modelo**. Y la BD lo cazó. Sin tests, sin reviews, sin nada: el `UNIQUE` salvó la coherencia.

### Paso 4 — Demostrar el N+1 (con el modelo aún mal, antes de corregir)

Vuelve a poner `hbm2ddl.auto=drop-and-create` y carga varios usuarios con un comentario cada uno (para que no salte el UNIQUE):

```java
em.getTransaction().begin();
for (int i = 0; i < 5; i++) {
    UserJpa u = new UserJpa(UserId.nuevo(), "user" + i + "@x.com", "User " + i);
    em.persist(u);
    em.persist(new CommentJpa(CommentId.nuevo(), u, PizzaId.nuevo(),
        "Comentario " + i, FechaComentario.ahora()));
}
em.getTransaction().commit();
em.clear();   // limpia el contexto para forzar SELECT desde BD

// Ahora leemos los comentarios:
List<CommentJpa> all = em.createQuery("SELECT c FROM CommentJpa c", CommentJpa.class)
    .getResultList();
```

Con `show_sql=true`, observa la consola. Verás algo así:

```sql
-- 1 query para los comentarios:
SELECT c.id, c.fecha, c.pizza_id, c.texto, c.user_id FROM comments c

-- + 5 queries (una por comentario) para cargar el autor EAGER:
SELECT u.id, u.email, u.nombre FROM users u WHERE u.id = ?
SELECT u.id, u.email, u.nombre FROM users u WHERE u.id = ?
SELECT u.id, u.email, u.nombre FROM users u WHERE u.id = ?
SELECT u.id, u.email, u.nombre FROM users u WHERE u.id = ?
SELECT u.id, u.email, u.nombre FROM users u WHERE u.id = ?
```

**1 + N = N+1.** Y eso con solo 5 usuarios. Con 5.000, son **5.001 consultas** para listar comentarios.

### Paso 5 — Corregir: volver a `@ManyToOne` LAZY

Cambia `CommentJpa.autor` de vuelta:

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "user_id", referencedColumnName = "id", nullable = false)
private UserJpa autor;
```

Vuelve a lanzar el DDL. El `UNIQUE` ha desaparecido:

```sql
create table comments (
    ...
    user_id uuid not null,
    constraint FK_comments_user foreign key (user_id) references users
    -- ← ya no hay UNIQUE
)
```

Y ahora el mismo usuario puede tener varios comentarios sin problemas.

### Paso 6 — Y el N+1, ¿se arregló? (no, todavía no)

Si vuelves a ejecutar el bucle de lectura y haces `c.getAutor().getNombre()` dentro:

```java
for (CommentJpa c : all) {
    System.out.println(c.getAutor().getNombre());
}
```

Verás **otra vez N+1**. Ahora con LAZY las queries se disparan al acceder a `getAutor()`. Mejor que EAGER (al menos solo pagas las que usas), pero igual de costoso si recorres todo.

**Solución correcta**: cargar todo de una con `JOIN FETCH`:

```java
List<CommentJpa> all = em.createQuery(
    "SELECT c FROM CommentJpa c JOIN FETCH c.autor", CommentJpa.class
).getResultList();
```

Con eso, **una sola query**:

```sql
SELECT c.*, u.*
FROM comments c
INNER JOIN users u ON u.id = c.user_id
```

> 📚 Esto es solo un anticipo: `JOIN FETCH` y N+1 son material del Bloque 5. Aquí basta con que los alumnos **vean** el problema y entiendan que `LAZY` no lo resuelve, solo lo aplaza.

### Mini-reto (3 min)

Tres preguntas para discutir:

1. Si modelas `User ↔ UserProfile` como `@OneToOne` bidireccional, **¿de qué lado conviene poner el `mappedBy`?** Es decir, ¿quién es el dueño?
2. ¿Por qué el `UNIQUE` en `comments.user_id` se considera un constraint **bueno** cuando la relación realmente es 1:1, y **malo** cuando no lo es?
3. ¿Qué le dirías a un colega que defiende dejar todo `EAGER` "para no tener que pensar en `JOIN FETCH`"?

> *Respuestas dirigidas:*
> 1. Suele ser dueño el que es **opcional** o el que **se crea después**. En `User-UserProfile`, normalmente el dueño es `UserProfile` (lleva la FK al `User`). `User` tiene `mappedBy="user"`.
> 2. Porque un constraint refleja una regla. Si la regla "un usuario tiene un perfil" es cierta, el `UNIQUE` te la blinda. Si la regla "un usuario tiene un comentario" es falsa, el `UNIQUE` te bloquea legítimamente.
> 3. Que `EAGER` no elimina el N+1, lo esconde dentro del `find`. El problema sigue ahí, peor: cargas datos que no necesitas, y cuando aparece el bug es difícil ver el origen porque "todo se hizo en el `find`". `LAZY` + `JOIN FETCH` cuando hace falta es la combinación profesional.

## 🎯 Cierre

Esta sección era atípica: en vez de aprender un patrón, hemos aprendido a **detectar uno mal aplicado**. Tres ideas para llevarse:

1. La cardinalidad del **lado** ("cada comentario tiene UN autor") no es la cardinalidad de la **relación** ("muchos comentarios pueden compartir autor"). `@ManyToOne`, no `@OneToOne`.
2. `@OneToOne` añade `UNIQUE`. Ese constraint es tu amigo si la relación realmente es 1:1, y tu carcelero si no lo es.
3. **El N+1 es un patrón, no una anotación**. EAGER lo hace tempranero pero no lo cura. La cura llega con consultas explícitas (`JOIN FETCH`), que veremos en el Bloque 5.
