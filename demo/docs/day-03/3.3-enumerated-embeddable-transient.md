# 3.3. `@Enumerated`, `@Embeddable`, `@Transient`

> **Duración estimada:** 25 min (8 min teoría + 17 min práctica)

---

## 🧠 Teoría rápida (8 min)

Hasta ahora en `PizzaJpa` y `IngredienteJpa` hemos "aplastado" los value objects: `Money` se convirtió en `BigDecimal`, `IngredienteId` en `UUID`. Funciona, pero **perdemos información semántica** en la capa JPA. Y eso a veces molesta: si quisiéramos hacer una `JPQL` filtrando por `coste.amount > 5`, querríamos un objeto `Money`, no un `BigDecimal` suelto.

Hoy vemos tres anotaciones que permiten respetar mejor la forma del dominio dentro de la entidad JPA:

### `@Embeddable` — "este objeto se mapea inline en la tabla"

Marca una clase (o **record**) como "incrustable" en otra entidad. Sus campos se mapean como **columnas adicionales** de la tabla padre. **No hay tabla nueva, no hay FK, no hay JOIN**.

```java
@Embeddable
public record Money(BigDecimal amount) {}
```

Y en la entidad:
```java
@Embedded
private Money coste;   // se mapeará como columna "amount" en la tabla
```

> ✅ **Hibernate 6 soporta records como `@Embeddable`**. Esto es lo que nos permite mantener `Money` y los `*Id` como records también en la capa de persistencia.
> ❌ **Los records NO pueden ser `@Entity`** (porque son `final` y JPA exige no-final + constructor sin args).

#### `@AttributeOverride` — renombrar columnas embebidas

Si el campo del record se llama `amount` pero quieres que la columna se llame `coste_eur`:

```java
@Embedded
@AttributeOverride(name = "amount", column = @Column(name = "coste_eur", nullable = false, precision = 10, scale = 2))
private Money coste;
```

Imprescindible cuando incrustas el **mismo** value object dos veces en la misma entidad (un `Money precioBase` y un `Money precioOferta` no pueden mapearse ambos a una columna `amount`).

### `@Enumerated` — "este enum se guarda en la BD"

Java tiene `enum`. SQL no. Dos formas de guardarlos:

```java
@Enumerated(EnumType.STRING)
private Tamano tamano;       // se guarda "PEQUENA", "MEDIANA", "GRANDE"
```

```java
@Enumerated(EnumType.ORDINAL)
private Tamano tamano;       // se guarda 0, 1, 2
```

> ⚠️ **Usa siempre `EnumType.STRING`**. El `ORDINAL` parece eficiente pero se rompe en cuanto alguien reordena el enum o inserta un valor nuevo en medio: una fila con `1` que significaba `MEDIANA` ahora significa otra cosa. Los bugs de este tipo son sutiles y dolorosos.

### `@Transient` — "ignora este campo"

Marca un atributo para que **JPA lo ignore por completo**: ni columna, ni guardado, ni leído.

```java
@Transient
private BigDecimal precioCalculado;
```

Útil cuando arrastras en la entidad JPA algo que no debe persistirse: cachés, valores derivados, banderas internas.

> 💡 **¿Y el `transient` de Java (sin arroba)?** Es el de serialización Java estándar. JPA respeta ambos: `transient` (palabra clave) o `@Transient` (anotación) excluyen el campo. Por consistencia, usa la anotación.

## 🛠 Práctica guiada (17 min)

Vamos a refactorizar `IngredienteJpa` y `PizzaJpa` para conservar `Money` y los IDs como value objects en la capa JPA. Veremos en disco que **no cambia el esquema** —seguimos teniendo las mismas columnas— pero el código gana expresividad.

### Paso 1 — Marcar los records como `@Embeddable`

Los records de dominio (`IngredienteId`, `PizzaId`, `Money`) ya existen. Lo que vamos a hacer es **anotarlos** para que JPA los reconozca como embebibles.

> 🚨 **Decisión arquitectónica importante.** Estamos a punto de añadir una anotación de `jakarta.persistence` a un record del paquete `domain`. **Eso rompe la regla** que establecimos en 3.1: el dominio no conoce JPA.
>
> Dos opciones para resolverlo correctamente:
>
> **Opción A (purista):** duplicar los records en `persistence/shared`: un `MoneyJpa`, un `IngredienteIdJpa`. El mapper traduce.
>
> **Opción B (pragmática):** aceptar que `@Embeddable` es una anotación tan ligera que el coste de la dependencia es menor que el beneficio de no duplicar. El dominio queda "manchado" con una anotación, pero sigue siendo un POJO compilable y testeable sin BD.
>
> **Para este curso elegimos B**, dejando constancia explícita de que la opción A existe y es defendible en proyectos donde el dominio debe ser 100% agnóstico (por ejemplo, si el mismo modelo se va a publicar como librería compartida).

Refactor de `Money` (en `domain/shared/`):

```java
package com.pizzeria.domain.shared;

import jakarta.persistence.Embeddable;
import java.math.BigDecimal;
import java.util.Objects;

@Embeddable
public record Money(BigDecimal amount) {

    public Money {
        Objects.requireNonNull(amount, "amount no puede ser null");
        if (amount.signum() < 0) {
            throw new IllegalArgumentException("Money no puede ser negativo: " + amount);
        }
    }
}
```

> 💬 Recuerda: los records exigen que JPA pueda construirlos. Hibernate 6 sabe hacerlo invocando el constructor canónico — por eso no necesitamos constructor sin args en un `@Embeddable` que sea record.

Lo mismo para `IngredienteId` y `PizzaId`:

```java
@Embeddable
public record IngredienteId(UUID value) {
    public IngredienteId {
        Objects.requireNonNull(value);
    }
    public static IngredienteId nuevo() {
        return new IngredienteId(UUID.randomUUID());
    }
}
```

### Paso 2 — Reescribir `IngredienteJpa` usando `@EmbeddedId` y `@Embedded`

```java
package com.pizzeria.persistence.ingrediente;

import com.pizzeria.domain.ingrediente.IngredienteId;
import com.pizzeria.domain.shared.Money;
import jakarta.persistence.*;

@Entity
@Table(name = "ingredientes")
public class IngredienteJpa {

    @EmbeddedId
    @AttributeOverride(name = "value", column = @Column(name = "id", nullable = false, updatable = false))
    private IngredienteId id;

    @Column(name = "nombre", nullable = false, length = 80, unique = true)
    private String nombre;

    @Embedded
    @AttributeOverride(name = "amount", column = @Column(name = "coste", nullable = false, precision = 10, scale = 2))
    private Money coste;

    protected IngredienteJpa() {}

    public IngredienteJpa(IngredienteId id, String nombre, Money coste) {
        this.id = id;
        this.nombre = nombre;
        this.coste = coste;
    }

    public IngredienteId getId() { return id; }
    public String getNombre() { return nombre; }
    public Money getCoste() { return coste; }
}
```

> 🔍 **Cambios respecto a 3.2:**
> - `@Id` → `@EmbeddedId` (porque ahora el id es un value object, no un tipo primitivo).
> - `BigDecimal coste` → `Money coste` con `@Embedded`.
> - El mapper se simplifica: ya no desempaqueta.

### Paso 3 — Simplificar el mapper

```java
package com.pizzeria.persistence.ingrediente;

import com.pizzeria.domain.ingrediente.Ingrediente;

public class IngredienteMapper {

    public IngredienteJpa toJpa(Ingrediente ingrediente) {
        return new IngredienteJpa(
            ingrediente.id(),
            ingrediente.nombre(),
            ingrediente.coste()
        );
    }

    public Ingrediente toDomain(IngredienteJpa jpa) {
        return Ingrediente.restore(
            jpa.getId(),
            jpa.getNombre(),
            jpa.getCoste()
        );
    }
}
```

> ✨ El mapper ahora es casi una identidad. Esa es la pista de que las dos capas están bien alineadas: el dominio y la entidad JPA dicen lo mismo, con propósitos distintos (negocio vs almacenamiento).

### Paso 5 — `@Transient` para el precio calculado (opcional)

El precio de la pizza es **calculado**, no almacenado. Pero supongamos que, por comodidad, queremos exponer un `BigDecimal precio` en `PizzaJpa` que el mapper pueda usar al reconstruir. Aquí entra `@Transient`:

```java
@Transient
private BigDecimal precioCalculado;

public void setPrecioCalculado(BigDecimal p) { this.precioCalculado = p; }
public BigDecimal getPrecioCalculado() { return precioCalculado; }
```

JPA ignora el campo. Si miras el DDL generado, **no aparece columna `precio_calculado`**.

> 💬 **¿Vale la pena?** En nuestro caso seguramente no: el precio se calcula en el dominio (`Pizza.precio()`) y no necesita viajar a la entidad JPA en absoluto. Lo enseñamos por completitud, porque `@Transient` aparece a menudo en proyectos reales donde alguien usó la entidad JPA como DTO de API REST y necesitaba campos derivados.

### Paso 6 — Verificar el DDL generado

Vuelve a lanzar el `Main` del 3.2 y mira el `create table` que escupe Hibernate:

```sql
create table ingredientes (
    id uuid not null,
    coste numeric(10,2) not null,
    nombre varchar(80) not null,
    primary key (id),
    unique (nombre)
)
```

> 🎯 **Punto clave:** el esquema es **idéntico** al que teníamos en 3.2. `@Embeddable` es una decisión **de código Java**, no de base de datos. La BD ni se entera.

---

## 🎯 Cierre

Hemos terminado de modelar los **value objects** dentro de la capa JPA. Cosas que se llevan:

- `@Embeddable` permite reutilizar los records de dominio (a costa de una anotación liviana).
- `@AttributeOverride` controla el nombre de columna cuando hace falta.
- `@Enumerated(EnumType.STRING)` para enums.
- `@Transient` para campos que no deben tocar la BD.

Y la idea grande: **el esquema SQL no cambia** entre la versión "aplastada" de 3.2 y esta. Lo único que cambia es la limpieza del código Java.

A partir de 3.4 entramos en relaciones. Ahí es donde Hibernate se pone interesante (y peligroso).
