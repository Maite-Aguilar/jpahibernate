# 3.4. Relaciones: `@ManyToOne`, `@OneToMany`, `@ManyToMany`, `@OneToOne`

> **Duración estimada:** 30 min (10 min teoría + 20 min práctica)

---

## 🧠 Teoría rápida (10 min)

Hasta aquí hemos mapeado tablas individuales. Ahora viene lo que separa "saber JPA" de "saber escribir `@Entity`": **las relaciones**.

### El catálogo

JPA define **cuatro cardinalidades**:

| Anotación | Significado en negocio (nuestro dominio) |
|---|---|
| `@ManyToOne` | Muchos `Comment` apuntan a un `User` (lado "muchos") |
| `@OneToMany` | Un `User` tiene muchos `Comment` (lado "uno") |
| `@ManyToMany` | Una `Pizza` tiene muchos `Ingrediente` y al revés |
| `@OneToOne` | Un `Comment` tiene un único `User` (caso especial, lo vemos en 3.7) |

> 💡 `@ManyToOne` y `@OneToMany` son **dos caras del mismo espejo**: la misma relación vista desde cada lado.

### Lo que SQL ya nos dice

Antes de tocar anotaciones, repasa lo que pasa en SQL:

- **1:N** → la tabla del lado "muchos" lleva una **FK** al lado "uno".
  `comments(id, texto, user_id)` ← `user_id` apunta a `users(id)`.
- **N:M** → necesitas una **tabla intermedia** con dos FKs.
  `pizza_ingrediente(pizza_id, ingrediente_id)`.
- **1:1** → cualquiera de los dos lados puede llevar la FK, con un constraint `UNIQUE`.

Cuando JPA pinta las relaciones, está generando exactamente este SQL. Tener esta imagen mental ayuda a entender por qué algunas anotaciones piden tantos detalles.

### Las dos preguntas que JPA exige responder

Para cualquier relación, JPA te obliga a decidir:

#### 1. ¿Bidireccional o unidireccional?

- **Unidireccional**: solo un lado conoce al otro. Más simple. Suficiente la mayoría de veces.
  *Ejemplo:* `PizzaJpa` tiene una lista de `IngredienteJpa`, pero `IngredienteJpa` no sabe en qué pizzas aparece.
- **Bidireccional**: ambos lados se conocen. Más cómodo para algunas consultas, pero **hay que tener cuidado de no caer en ciclos infinitos** (sobre todo en `toString` o serialización JSON).

> **Regla práctica:** empieza unidireccional. Hazlo bidireccional **cuando lo necesites de verdad**, no "por si acaso".

#### 2. ¿Quién es el lado propietario?

En SQL, la FK está en una tabla concreta. En JPA, el "lado propietario" es **el que decide cuándo se inserta/actualiza esa FK**. Lo veremos en detalle en 3.5; aquí basta con saber que se elige con `mappedBy`.

### Las dos preguntas que JPA NO pregunta pero deberías responder

#### 3. ¿Eager o lazy?

¿Cuándo se cargan los objetos relacionados?

- **EAGER**: al cargar la entidad, se cargan también los relacionados. Cómodo. Peligroso si la cadena se hace grande (cargas medio mundo sin querer).
- **LAZY**: se cargan cuando se accede a ellos. Eficiente. Puede explotar con un `LazyInitializationException` si la sesión está cerrada.

**Defaults de JPA** (memorízalos, son tramposos):

| Anotación | Default |
|---|---|
| `@ManyToOne` | **EAGER** |
| `@OneToOne` | **EAGER** |
| `@OneToMany` | LAZY |
| `@ManyToMany` | LAZY |

> ⚠️ Los defaults `EAGER` de `@ManyToOne` y `@OneToOne` son la fuente número uno de problemas N+1 en proyectos reales. **Pondremos LAZY explícitamente siempre** y luego decidiremos qué cargar con `JOIN FETCH` (Bloque 5).

#### 4. ¿Cascade?

Cuando guardes/borres la entidad padre, ¿qué pasa con la hija?

- `CascadeType.PERSIST` → al persistir el padre, persiste también los hijos nuevos.
- `CascadeType.MERGE`, `REMOVE`, `REFRESH`, `DETACH`, `ALL`…

> ⚠️ **`CascadeType.ALL` + `@ManyToMany` es casi siempre un error.** Borrar una pizza no debería borrar sus ingredientes (otras pizzas los usan). Cascadas mal puestas borran datos compartidos. Lo discutimos en 3.6.

### Aplicado a nuestro dominio

| Relación | Tipo | Bidir? | Cascade |
|---|---|---|---|
| `Pizza` ↔ `Ingrediente` | `@ManyToMany` | Unidireccional (Pizza → Ingrediente) | NINGUNA. Ingredientes son entidades independientes. |
| `User` → `Comment` | `@OneToMany` / `@ManyToOne` | Lo veremos en 3.7 | A discutir |
| `Comment` → `User` | `@OneToOne` | Caso patológico, lo abordamos en 3.7 | — |

### El gran principio: agregados marcan la frontera

Recuerda el Bloque 2: definimos que **`Ingrediente` está dentro del agregado `Pizza`** (cargamos los ingredientes con la pizza, son parte de "qué es esta pizza"). En cambio, **`Comment` está fuera del agregado** (puede haber miles, los cargamos bajo demanda).

Esa decisión **dicta la estrategia de carga**:

- Dentro del agregado → cargamos con la raíz (usamos `JOIN FETCH` cuando hace falta).
- Fuera del agregado → siempre lazy, navegación explícita por id.

Esto **no es opinión**: es lo que evita que tu sistema cargue 200 comentarios cada vez que muestras una pizza en el menú.

## 🛠 Práctica guiada (20 min)

Vamos a modelar **la relación N:M entre Pizza e Ingrediente** completa, cerrando las cuatro capas (dominio, entidad JPA, mapper, repository) que comenzamos.

### Paso 1 — Recordar cómo está la relación en el dominio (Bloque 2)

En el dominio que ya tenemos:

```java
// (extracto, Pizza.java del Bloque 2)
public class Pizza {
    private final PizzaId id;
    private String nombre;
    private List<Ingrediente> ingredientes;

    private Pizza(PizzaId id, String nombre, List<Ingrediente> ingredientes) { ... }

    public static Pizza create(String nombre, List<Ingrediente> ingredientes) {
        if (ingredientes == null || ingredientes.isEmpty()) {
            throw new IllegalArgumentException("Una pizza necesita al menos un ingrediente");
        }
        return new Pizza(PizzaId.nuevo(), nombre, new ArrayList<>(ingredientes));
    }

    public static Pizza restore(PizzaId id, String nombre, List<Ingrediente> ingredientes) {
        return new Pizza(id, nombre, new ArrayList<>(ingredientes));
    }

    public Money precio() {
        BigDecimal subtotal = ingredientes.stream()
            .map(i -> i.coste().amount())
            .reduce(BigDecimal.ZERO, BigDecimal::add);
        return new Money(subtotal.multiply(new BigDecimal("1.20")));
    }
    // ...
}
```

> ✅ **Importante**: el dominio guarda la lista de `Ingrediente` (objetos completos, no ids). Es así porque calcular el precio requiere conocer el coste de cada ingrediente — y porque, conceptualmente, "una pizza es su nombre **más sus ingredientes**".

### Paso 2 — Diseñar la tabla intermedia (en SQL puro, mentalmente)

```sql
create table pizzas (
    id uuid primary key,
    nombre varchar(100) not null unique
);

create table ingredientes (
    id uuid primary key,
    nombre varchar(80) not null unique,
    coste numeric(10,2) not null
);

create table pizza_ingrediente (
    pizza_id      uuid not null,
    ingrediente_id uuid not null,
    primary key (pizza_id, ingrediente_id),
    foreign key (pizza_id)      references pizzas (id),
    foreign key (ingrediente_id) references ingredientes (id)
);
```

Esta es la imagen mental. Ahora veamos cómo decirle a JPA que la pinte.

### Paso 3 — `@ManyToMany` en `PizzaJpa`

```java
package com.pizzeria.persistence.pizza;

import com.pizzeria.domain.pizza.PizzaId;
import com.pizzeria.persistence.ingrediente.IngredienteJpa;
import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "pizzas")
public class PizzaJpa {

    @EmbeddedId
    @AttributeOverride(name = "value", column = @Column(name = "id", nullable = false, updatable = false))
    private PizzaId id;

    @Column(name = "nombre", nullable = false, length = 100, unique = true)
    private String nombre;

    @ManyToMany(fetch = FetchType.LAZY)
    @JoinTable(
        name = "pizza_ingrediente",
        joinColumns        = @JoinColumn(name = "pizza_id",       referencedColumnName = "id"),
        inverseJoinColumns = @JoinColumn(name = "ingrediente_id", referencedColumnName = "id")
    )
    private List<IngredienteJpa> ingredientes = new ArrayList<>();

    protected PizzaJpa() {}

    public PizzaJpa(PizzaId id, String nombre, List<IngredienteJpa> ingredientes) {
        this.id = id;
        this.nombre = nombre;
        this.ingredientes = new ArrayList<>(ingredientes);
    }

    public PizzaId getId() { return id; }
    public String getNombre() { return nombre; }
    public List<IngredienteJpa> getIngredientes() { return ingredientes; }
}
```

> 🔍 **Diseccionando la anotación:**
> - `fetch = LAZY` — explícito aunque ya es el default. Mañana añadimos un comentario en una review y nadie tiene que ir a buscarlo.
> - `@JoinTable` — describe la tabla intermedia.
>   - `name` — nombre de la tabla puente.
>   - `joinColumns` — columna que apunta a la tabla "de este lado" (Pizza).
>   - `inverseJoinColumns` — columna que apunta al otro lado (Ingrediente).
> - **No hay `cascade`**: si borramos una pizza, no queremos borrar los ingredientes. Solo se borrarán las filas de `pizza_ingrediente` (las filas de la tabla intermedia las maneja Hibernate automáticamente al actualizar la colección).

### Paso 4 — `PizzaMapper` completo

```java
package com.pizzeria.persistence.pizza;

import com.pizzeria.domain.pizza.Pizza;
import com.pizzeria.persistence.ingrediente.IngredienteJpa;
import com.pizzeria.persistence.ingrediente.IngredienteMapper;

import java.util.List;

public class PizzaMapper {

    private final IngredienteMapper ingredienteMapper;

    public PizzaMapper(IngredienteMapper ingredienteMapper) {
        this.ingredienteMapper = ingredienteMapper;
    }

    public PizzaJpa toJpa(Pizza pizza) {
        List<IngredienteJpa> ingredientesJpa = pizza.ingredientes().stream()
            .map(ingredienteMapper::toJpa)
            .toList();
        return new PizzaJpa(pizza.id(), pizza.nombre(), ingredientesJpa);
    }

    public Pizza toDomain(PizzaJpa jpa) {
        var ingredientes = jpa.getIngredientes().stream()
            .map(ingredienteMapper::toDomain)
            .toList();
        return Pizza.restore(jpa.getId(), jpa.getNombre(), ingredientes);
    }
}
```

> 🧠 **Una sutileza importante.** Cuando hagamos `toJpa(pizza)`, los `IngredienteJpa` que pasamos a `PizzaJpa` **no son necesariamente los mismos que ya existen en BD**. Si simplemente los insertásemos, Hibernate intentaría volver a crearlos y fallaría por `UNIQUE`. La forma correcta en el repository será **buscar primero los ingredientes en la sesión actual** (con `em.find`) y reutilizarlos.
>
> Lo veremos en detalle al implementar el repository. Por ahora, basta saber que **el mapper produce instancias "candidatas"** y el repository decide qué hacer con ellas.

### Paso 5 — Lanzar y mirar el DDL

Vuelve a ejecutar `Main`. Deberías ver:

```sql
create table pizza_ingrediente (

alter table pizza_ingrediente

    add constraint FK_pi_ingrediente foreign key (ingrediente_id) references ingredientes
```

✅ Hibernate ha pintado exactamente lo que dibujamos en el paso 2.

### Paso 6 — Esbozar el `PizzaRepository` (implementación completa en Bloque 4)

```java
package com.pizzeria.persistence.pizza;

import com.pizzeria.domain.pizza.Pizza;
import com.pizzeria.domain.pizza.PizzaId;
import jakarta.persistence.EntityManager;
import java.util.Optional;

public class PizzaRepository {

    private final EntityManager em;
    private final PizzaMapper mapper;

    public PizzaRepository(EntityManager em, PizzaMapper mapper) {
        this.em = em;
        this.mapper = mapper;
    }

    public void save(Pizza pizza) {
        PizzaJpa jpa = mapper.toJpa(pizza);
        em.persist(jpa);     // simplificado: en 4.x manejamos managed/detached
    }

    public Optional<Pizza> findById(PizzaId id) {
        PizzaJpa jpa = em.find(PizzaJpa.class, id);
        return Optional.ofNullable(jpa).map(mapper::toDomain);
    }
}
```

> 🚧 **Está incompleto a propósito.** Falta:
> - Cómo reutilizar ingredientes ya existentes para no duplicarlos.
> - Cómo gestionar la transacción.
> - Qué pasa si la pizza ya existe (`merge` vs `persist`).
>
> Eso es justo el contenido del Bloque 4. Aquí hemos cerrado **el modelado de la relación**.

### Mini-reto (5 min)

Mira el `@ManyToMany` que escribimos. Las preguntas:

1. ¿Es bidireccional? ¿Cómo lo sabes mirando el código?
2. Si un alumno te pregunta "¿cómo hago para saber, dado un `Ingrediente`, en qué pizzas aparece?", ¿qué le respondes? Tres opciones:
   - (a) Hacerla bidireccional añadiendo `@ManyToMany(mappedBy="ingredientes")` en `IngredienteJpa`.
   - (b) Consultar con una JPQL ad-hoc.
   - (c) Aceptar la limitación porque no es una pregunta del agregado.
3. ¿Qué decisión tomarías y por qué?

> *Pista para la discusión:* la pregunta "en qué pizzas aparece este ingrediente" es **de inventario**, no del agregado `Pizza`. Convertir la relación en bidireccional solo para esa query es un coste perpetuo (ciclos en `toString`, peligro de `JOIN FETCH` mal usado…) para resolver algo que una JPQL hace en una línea. La respuesta defendible es (b) o (c).

## 🎯 Cierre

Hemos modelado la relación N:M Pizza-Ingrediente con todas sus capas:

- **Dominio** → lista de `Ingrediente` (objetos del dominio).
- **JPA** → `@ManyToMany` con `@JoinTable` explícita.
- **Mapper** → traduce listas en ambos sentidos.
- **Repository** → esbozado (lo cerramos en Bloque 4).

Las dos decisiones grandes:
- **Unidireccional** (Pizza conoce a Ingrediente, no al revés).
- **Lazy explícito**, aunque sea el default.

En **3.5** profundizamos en `mappedBy` y el concepto de lado propietario, que se entiende mejor con la relación 1:N (`User → Comment`). En **3.6** volvemos al N:M para ver qué pasa cuando la relación tiene atributos propios (por ejemplo, una cantidad de cada ingrediente).
