# 3.8. Bean Validation en la entidad: complemento, no sustituto del dominio

> **Duración estimada:** 20 min (8 min teoría + 12 min práctica)

---

## 🧠 Teoría rápida (8 min)

Llegamos al cierre del Bloque 3. Antes de seguir al `EntityManager` y las transacciones, queda una pregunta importante: **¿dónde van las validaciones?**

Si volvemos al Bloque 2, decíamos que las invariantes viven en el dominio. `Money` no puede ser negativo, `Pizza` necesita al menos un ingrediente, `FechaComentario` no puede estar en el futuro. Todo eso se valida en los `create()` de los POJOs.

Pero existe **Bean Validation** (JSR 380, `jakarta.validation`): un estándar para validar objetos con anotaciones tipo `@NotNull`, `@Size`, `@Min`, `@Email`, `@Past`… ¿Hay que usarlo en la entidad JPA? ¿Sustituye al dominio? ¿Lo complementa?

### Qué es Bean Validation

Un estándar de **validación declarativa** que se aplica sobre cualquier POJO con anotaciones:

```java
public class CrearPizzaDTO {
    @NotBlank
    @Size(max = 100)
    private String nombre;

    @NotEmpty
    private List<@NotNull UUID> ingredientesIds;
}
```

Un `Validator` (Hibernate Validator es la implementación más usada) recorre el objeto y devuelve violaciones:

```java
Set<ConstraintViolation<CrearPizzaDTO>> errores = validator.validate(dto);
```

JPA, además, **integra Bean Validation automáticamente**: antes de un `INSERT/UPDATE`, valida la entidad. Si hay violaciones, lanza `ConstraintViolationException`.

### El problema cuando ya tienes invariantes en el dominio

Pongamos que la regla de negocio es "el nombre de la pizza no puede estar vacío y tiene máximo 100 caracteres".

Si la ponemos en **el dominio**:

```java
// Pizza.java
public static Pizza create(String nombre, ...) {
    if (nombre == null || nombre.isBlank()) {
        throw new IllegalArgumentException("Nombre obligatorio");
    }
    if (nombre.length() > 100) {
        throw new IllegalArgumentException("Nombre demasiado largo");
    }
    // ...
}
```

Y **también** en la entidad JPA:

```java
// PizzaJpa.java
@NotBlank
@Size(max = 100)
@Column(name = "nombre", nullable = false, length = 100)
private String nombre;
```

…estamos **duplicando la regla**. Y la duplicación es enemiga del mantenimiento: si mañana sube a 150, hay que cambiarla en dos sitios. Si nos olvidamos de uno, los datos divergen.

### La pregunta: ¿dónde poner cada validación?

**La respuesta corta**: depende de **qué tipo de regla** es.

#### Reglas de negocio (invariantes)

> "Una pizza necesita al menos un ingrediente."
> "El precio no puede ser negativo."
> "La fecha de un comentario no puede ser futura."

Estas son **del dominio**. Existirían **aunque no hubiera base de datos**. Van en `Pizza`, `Money`, `FechaComentario`. No las dupliques en JPA.

#### Reglas de almacenamiento (constraints)

> "La columna no puede ser NULL."
> "La columna `email` es UNIQUE."
> "El VARCHAR tiene tamaño 200."

Estas son **de la BD**. Van en `@Column(nullable = false, length = 200, unique = true)`. Son la última línea de defensa **a nivel físico**, y son explícitas en SQL.

#### Reglas de entrada (DTOs y APIs)

> "El cliente HTTP nos manda un nombre que no debe estar vacío y debe ser email válido."

Estas van en los **DTOs de entrada**, no en la entidad JPA ni en el dominio. Es validación de input, propia de la capa de presentación/API.

### Las tres capas, con un ejemplo

| Capa | Regla | Cómo |
|---|---|---|
| **DTO de entrada** (REST) | "El payload trae un nombre no vacío" | `@NotBlank` en el DTO |
| **Dominio** | "Una pizza no existe sin nombre, y el nombre no puede pasar de 100 chars" | `if/throw` en `Pizza.create()` |
| **Entidad JPA** | "La columna `nombre` no admite NULL y guarda VARCHAR(100)" | `@Column(nullable=false, length=100)` |

> 💡 **No se duplica nada**. Cada capa expresa la regla **en sus propios términos**, en su nivel de abstracción.

### ¿Y entonces Bean Validation en la entidad JPA cuándo?

Tres casos donde sí tiene sentido:

1. **Cuando la entidad JPA es también el "objeto que entra"** en una arquitectura simple sin DTOs. (No es nuestro caso, pero es común en CRUDs pequeños.)
2. **Como red de seguridad** ante datos que entran por otra vía (importación, scripts, otra aplicación que escribe en la misma tabla y no pasa por tu dominio).
3. **Para reglas que no tienen un equivalente en SQL** (`@Email` no es algo que `VARCHAR` valide; `@Past` no se expresa en un constraint estándar).

Pero **nunca como reemplazo de las invariantes del dominio**. Esa es la pieza no negociable.

### Una nota sobre `@Valid` en cascada

Si la entidad JPA contiene otros objetos y quieres validarlos en cascada, se hace con `@Valid`:

```java
@Embedded
@Valid
private Money coste;
```

Cuando JPA valide la entidad antes de persistir, también validará `Money`. **Hibernate Validator** lo aplica de forma transparente.

## 🛠 Práctica guiada (12 min)

Vamos a aplicar Bean Validation **solo donde aporta** y a dejar claro qué responsabilidad tiene cada capa.

### Paso 1 — Añadir Hibernate Validator al `pom.xml`

```xml
<dependency>
    <groupId>org.hibernate.validator</groupId>
    <artifactId>hibernate-validator</artifactId>
    <version>8.0.1.Final</version>
</dependency>
<dependency>
    <groupId>org.glassfish.expressly</groupId>
    <artifactId>expressly</artifactId>
    <version>5.0.0</version>
</dependency>
```

### Paso 2 — Caso justificable: validación de `email` en `UserJpa`

La regla "es un email" **no se puede expresar bien en SQL**. Un `@Column(name = "email")` no valida el formato. Aquí Bean Validation sí aporta.

```java
@Entity
@Table(name = "users")
public class UserJpa {

    @EmbeddedId
    @AttributeOverride(name = "value", column = @Column(name = "id", nullable = false))
    private UserId id;

    @Email                                                 // ← Bean Validation
    @NotBlank
    @Column(name = "email", nullable = false, length = 200, unique = true)
    private String email;

    @NotBlank
    @Size(max = 100)
    @Column(name = "nombre", nullable = false, length = 100)
    private String nombre;

    // resto igual...
}
```

> 🤔 **¿No habíamos dicho que no se duplica?** Lo dijimos para reglas que **el dominio ya cubre**. Aquí asumimos que el dominio `User.create(email, nombre)` valida que el email no sea null/blank — pero **no** que tenga formato de email (eso sería una librería de regex que mejor delegamos). Bean Validation cubre justo esa pieza.
>
> En general: **si el dominio valida la regla**, no la repitas. **Si solo la valida la presentación o no se valida en ninguna parte aún**, ponla aquí o en el DTO según convenga. Sé explícito en la decisión.

### Paso 3 — Caso NO duplicar: nombre de pizza

En `Pizza` (dominio) ya tenemos:

```java
public static Pizza create(String nombre, List<IngredienteEnPizza> ingredientes) {
    if (nombre == null || nombre.isBlank()) {
        throw new IllegalArgumentException("Nombre obligatorio");
    }
    if (nombre.length() > 100) {
        throw new IllegalArgumentException("Nombre demasiado largo");
    }
    // ...
}
```

Y en `PizzaJpa`:

```java
@Column(name = "nombre", nullable = false, length = 100, unique = true)
private String nombre;
```

**No vamos a añadir `@NotBlank @Size(max=100)`**. La regla está en el dominio (donde pertenece) y la BD la protege como constraint físico. Bean Validation no aportaría nada nuevo: solo duplicación.

### Paso 4 — Activar Hibernate Validator y ver el flujo

Bean Validation **se ejecuta automáticamente** antes de cada `INSERT/UPDATE` si la dependencia está en el classpath. No hay que hacer nada más.

Prueba a forzar un error:

```java
em.getTransaction().begin();
UserJpa malo = new UserJpa(UserId.nuevo(), "esto-no-es-email", "Test");
em.persist(malo);
em.getTransaction().commit();
```

Resultado:

```
jakarta.validation.ConstraintViolationException:
Validation failed for classes [com.pizzeria.persistence.user.UserJpa]
during persist time for groups [jakarta.validation.groups.Default]
List of constraint violations:[
    ConstraintViolationImpl{interpolatedMessage='must be a well-formed email address',
                            propertyPath=email, ...}
]
```

✅ La validación dispara **antes** de tocar la BD. Hibernate ni siquiera lanza el `INSERT`.

### Paso 5 — Tabla de decisión: ¿dónde va cada regla?

Resumen práctico para los alumnos:

| Regla | Dominio | Entidad JPA (`@Column`) | Bean Validation | DTO API |
|---|:-:|:-:|:-:|:-:|
| `Pizza` necesita ≥ 1 ingrediente | ✅ | — | — | — |
| Nombre pizza no vacío | ✅ | `nullable=false` | — | ✅ |
| Nombre pizza ≤ 100 chars | ✅ | `length=100` | — | ✅ |
| `Money` no negativo | ✅ | — | — | — |
| `email` con formato válido | (parcial) | `nullable=false` | ✅ (`@Email`) | ✅ |
| `email` único | — | `unique=true` | — | — |
| `FechaComentario` no futura | ✅ | — | — | — |
| Pizza-Ingrediente único (pizza_id, ingrediente_id) | — | `@UniqueConstraint` | — | — |

> 🔑 **Lectura horizontal**: una regla puede aparecer en **varias capas a la vez** sin ser duplicación, siempre que cada capa la exprese **en sus propios términos** y por **su propia razón**. La duplicación dañina es repetir la **misma lógica de validación** dos veces con `if/throw` o con la misma anotación.

### Mini-reto (3 min)

Tres situaciones para clasificar — ¿dónde poner la regla?

1. "El usuario debe tener al menos 18 años para registrarse."
2. "El payload de creación trae como mínimo un ingrediente_id en la lista."
3. "Después de 30 días sin actividad, el usuario se marca inactivo."

> *Respuestas guiadas:*
> 1. **Dominio**. Es una regla de negocio. `User.create()` la valida.
> 2. **DTO API**. Es una regla de entrada (`@NotEmpty` en el DTO). El dominio también valida que `Pizza` tenga al menos un ingrediente, pero a otro nivel.
> 3. Es un **proceso**, no una invariante. Pertenece a un **servicio** (`UsuarioInactividadService`) que se ejecuta periódicamente. No va en validaciones de campo en ningún sitio.

## 🎯 Cierre del Bloque 3

Hemos cerrado las anotaciones JPA, las relaciones (N:M, 1:N, 1:1) y la validación. El esqueleto del Bloque 3 queda así:

```
domain/                  ← POJOs puros con invariantes
persistence/
   pizza/
      PizzaJpa            ← @Entity, @OneToMany a PizzaIngredienteJpa
      PizzaIngredienteJpa ← entidad asociativa con cantidad
      PizzaMapper
      PizzaRepository (esqueleto)
   ingrediente/
      IngredienteJpa
      IngredienteMapper
      IngredienteRepository (esqueleto)
   user/
      UserJpa             ← @Email + @Column unique
      UserMapper
   comment/
      CommentJpa          ← @ManyToOne LAZY a UserJpa, PizzaId embebido
      CommentMapper
```

Ideas no negociables del bloque:

1. **El dominio no sabe de JPA**. Lo único permitido es `@Embeddable` en los value objects (decisión pragmática, defendible).
2. **Cada capa tiene una sola responsabilidad**. Dominio modela, entidad guarda, mapper traduce, repository orquesta.
3. **Relaciones unidireccionales por defecto**. Bidireccional solo cuando lo exige el caso real.
4. **`LAZY` explícito siempre**. Defaults `EAGER` solo traen sorpresas.
5. **N:M con atributos = entidad asociativa**. Sin excusas.
6. **Bean Validation complementa, no sustituye**.

A partir de aquí, el Bloque 4 se mete en lo que **realmente hace** Hibernate cuando ejecutas: `EntityManager`, contexto de persistencia, estados, dirty checking, transacciones. Hoy hemos diseñado el modelo; mañana lo ponemos en marcha.
