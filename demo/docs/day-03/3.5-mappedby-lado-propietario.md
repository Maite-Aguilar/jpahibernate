# 3.5. `mappedBy`, `@JoinColumn`, `@JoinTable`: lado propietario vs inverso

> **Duración estimada:** 25 min (8 min teoría + 17 min práctica)

---

## 🧠 Teoría rápida (8 min)

En 3.4 mencionamos el "lado propietario" como algo que decidiremos después. Es ahora. Esta sección es la más conceptual del Bloque 3, y la que más errores produce en proyectos reales si no se entiende.

### El problema: SQL solo tiene un sitio para la FK

Cuando hablamos de "Comment apunta a User", en SQL eso significa **una sola cosa**:

```sql
create table comments (
    id      uuid primary key,
    texto   text not null,
    user_id uuid not null,            -- la FK vive AQUÍ, en esta tabla
    foreign key (user_id) references users(id)
);
```

La FK está en una tabla concreta. Y solo hay **un** `INSERT/UPDATE` que la modifica.

Pero en Java, si la relación es **bidireccional**, hay **dos caminos** para "saber" sobre esa relación:

```java
Comment c = ...;
c.getAutor();         // Comment → User

User u = ...;
u.getComments();      // User → Comments
```

JPA necesita decidir: cuando llamo a `em.persist()` o cambio una colección, **¿qué lado activa el `UPDATE` de la FK?** Si los dos lados pudieran, escribirían el doble (o se contradirían).

### La respuesta: un lado es propietario, el otro es inverso

- **Lado propietario**: el que **lleva** la información de la FK. Cuando este lado cambia, JPA emite el `UPDATE`.
- **Lado inverso**: el que **refleja** la relación pero **no la controla**. Cambiarlo en código no produce SQL.

> 🔑 **Regla de oro**: el lado propietario es **siempre el que físicamente tiene la FK en SQL**. En 1:N, ese es el lado "muchos".

### `mappedBy` — la señal de "yo soy el inverso"

`mappedBy` se pone en **el lado inverso** y dice: "la información de esta relación está en el otro lado, en el atributo X".

```java
// Comment.java (LADO PROPIETARIO — aquí está la FK)
@ManyToOne
@JoinColumn(name = "user_id")
private UserJpa autor;

// User.java (LADO INVERSO — refleja, no controla)
@OneToMany(mappedBy = "autor")
private List<CommentJpa> comments;
```

> 💡 `mappedBy = "autor"` se lee: "mi colección `comments` está mapeada **por** el atributo `autor` del otro lado".

### `@JoinColumn` vs `@JoinTable`

| Anotación | Cuándo | Genera |
|---|---|---|
| `@JoinColumn` | Cuando la FK vive en una columna del propio lado | `user_id` en `comments` |
| `@JoinTable` | Cuando la relación necesita tabla intermedia (N:M) | `pizza_ingrediente` |

Lo usaste ya en 3.4: la N:M Pizza-Ingrediente usó `@JoinTable`. Si fuese 1:N, usarías `@JoinColumn`.

### El error clásico: olvidar `mappedBy`

Si modelas una bidireccional **sin** `mappedBy` en el inverso:

```java
// Comment.java
@ManyToOne
@JoinColumn(name = "user_id")
private UserJpa autor;

// User.java — ¡SIN mappedBy!
@OneToMany
private List<CommentJpa> comments;
```

JPA piensa que son **dos relaciones distintas** y… genera una **tabla intermedia** que no querías:

```sql
create table users_comments (
    user_id    uuid,
    comment_id uuid
);
```

Y ahora tienes la FK `user_id` en `comments` (que sí necesitabas) **más** la tabla puente fantasma. Bug silencioso.

> ⚠️ Síntoma del problema: si miras el DDL generado y aparece una tabla intermedia que no esperabas, te falta `mappedBy`.

### Sincronizar ambos lados — responsabilidad tuya

Aunque JPA solo persiste lo que dice el lado propietario, **en memoria** ambos lados deben ser coherentes. Si añades un `Comment` a un `User` solo por un lado, te quedas con datos inconsistentes hasta que recargues.

Patrón habitual: **método "addX"** en el lado propietario (o en el agregado raíz) que actualiza los dos.

```java
public void asignarA(UserJpa user) {
    this.autor = user;
    user.getComments().add(this);  // sincronizamos el lado inverso
}
```

> 💡 Pero ojo: esto **solo lo necesitas si la relación es bidireccional en JPA**. En nuestro caso, vamos a mantenerlo **unidireccional siempre que podamos**, y nos ahorraremos este patrón.

## 🛠 Práctica guiada (17 min)

Vamos a introducir `User` y `Comment` en el dominio y modelar la relación 1:N entre ellos. Nuestra postura por defecto: **unidireccional**. Solo discutiremos qué cambiaría si la quisiéramos bidireccional.

### Paso 1 — Dominio: `User` y `Comment` (recordatorio del Bloque 2)

Asumimos que en el Bloque 2 ya están modelados así:

**`User.java`** (dominio)
```java
package com.pizzeria.domain.user;

public class User {
    private final UserId id;
    private String email;
    private String nombre;

    private User(UserId id, String email, String nombre) { ... }

    public static User create(String email, String nombre) {
        // valida email, nombre no vacío…
        return new User(UserId.nuevo(), email, nombre);
    }

    public static User restore(UserId id, String email, String nombre) {
        return new User(id, email, nombre);
    }
    // ...
}
```

**`Comment.java`** (dominio)
```java
package com.pizzeria.domain.comment;

public class Comment {
    private final CommentId id;
    private final UserId autorId;        // ← referencia por ID, no objeto
    private final PizzaId pizzaId;
    private String texto;
    private final FechaComentario fecha;

    private Comment(...) { ... }

    public static Comment create(UserId autor, PizzaId pizza, String texto) { ... }
    public static Comment restore(...) { ... }
    // ...
}
```

> 🧠 **Decisión de dominio importante:** `Comment` referencia al usuario **por id** (`UserId`), no por objeto (`User`). ¿Por qué?
>
> Porque `Comment` está **fuera del agregado `User`**. Tener un objeto completo `User` dentro de `Comment` arrastraría toda la entidad cada vez que cargas un comentario, y borraría la frontera del agregado. La referencia por id es la forma DDD-correcta de relacionar agregados distintos: "yo conozco *quién*, no *todo lo suyo*".
>
> En la **capa JPA** podemos optar por el objeto completo (`UserJpa autor`) para que JPA gestione la FK cómodamente. El mapper hace la traducción.

### Paso 2 — `UserJpa` (sin relaciones)

```java
package com.pizzeria.persistence.user;

import com.pizzeria.domain.user.UserId;
import jakarta.persistence.*;

@Entity
@Table(name = "users")
public class UserJpa {

    @EmbeddedId
    @AttributeOverride(name = "value", column = @Column(name = "id", nullable = false, updatable = false))
    private UserId id;

    @Column(name = "email", nullable = false, length = 200, unique = true)
    private String email;

    @Column(name = "nombre", nullable = false, length = 100)
    private String nombre;

    protected UserJpa() {}

    public UserJpa(UserId id, String email, String nombre) {
        this.id = id;
        this.email = email;
        this.nombre = nombre;
    }

    public UserId getId() { return id; }
    public String getEmail() { return email; }
    public String getNombre() { return nombre; }
}
```

Nada nuevo: igual que `IngredienteJpa`.

### Paso 3 — `CommentJpa` con `@ManyToOne` unidireccional

```java
package com.pizzeria.persistence.comment;

import com.pizzeria.domain.comment.CommentId;
import com.pizzeria.domain.comment.FechaComentario;
import com.pizzeria.domain.pizza.PizzaId;
import com.pizzeria.persistence.user.UserJpa;
import jakarta.persistence.*;

@Entity
@Table(name = "comments")
public class CommentJpa {

    @EmbeddedId
    @AttributeOverride(name = "value", column = @Column(name = "id", nullable = false, updatable = false))
    private CommentId id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "user_id", referencedColumnName = "id", nullable = false)
    private UserJpa autor;

    // La pizza la referenciamos solo por id: está en OTRO agregado
    @Embedded
    @AttributeOverride(name = "value", column = @Column(name = "pizza_id", nullable = false, updatable = false))
    private PizzaId pizzaId;

    @Column(name = "texto", nullable = false, length = 1000)
    private String texto;

    @Embedded
    @AttributeOverride(name = "value", column = @Column(name = "fecha", nullable = false, updatable = false))
    private FechaComentario fecha;

    protected CommentJpa() {}

    public CommentJpa(CommentId id, UserJpa autor, PizzaId pizzaId, String texto, FechaComentario fecha) {
        this.id = id;
        this.autor = autor;
        this.pizzaId = pizzaId;
        this.texto = texto;
        this.fecha = fecha;
    }

    public CommentId getId() { return id; }
    public UserJpa getAutor() { return autor; }
    public PizzaId getPizzaId() { return pizzaId; }
    public String getTexto() { return texto; }
    public FechaComentario getFecha() { return fecha; }
}
```

> 🔍 **Decisiones a comentar con los alumnos:**
> - `@ManyToOne(fetch = LAZY, optional = false)` — explícitamente perezoso, y no admite null (todo comentario tiene autor).
> - `@JoinColumn(name = "user_id")` — la FK es la columna `user_id` en `comments`. **Aquí vive la relación.**
> - `pizzaId` se mapea como `@Embedded`, **no como `@ManyToOne`**. Diferencia clave: respetamos que `Pizza` es otro agregado.
> - **No hay relación inversa en `UserJpa`**: la relación es unidireccional Comment→User.

### Paso 4 — Mapper de `Comment`

```java
package com.pizzeria.persistence.comment;

import com.pizzeria.domain.comment.Comment;
import com.pizzeria.domain.user.UserId;
import com.pizzeria.persistence.user.UserJpa;
import jakarta.persistence.EntityManager;

public class CommentMapper {

    public CommentJpa toJpa(Comment comment, EntityManager em) {
        // Necesitamos el UserJpa correspondiente, no inventarlo:
        UserJpa autor = em.getReference(UserJpa.class, comment.autorId());
        return new CommentJpa(
            comment.id(),
            autor,
            comment.pizzaId(),
            comment.texto(),
            comment.fecha()
        );
    }

    public Comment toDomain(CommentJpa jpa) {
        return Comment.restore(
            jpa.getId(),
            jpa.getAutor().getId(),  // del objeto JPA extraemos solo el ID
            jpa.getPizzaId(),
            jpa.getTexto(),
            jpa.getFecha()
        );
    }
}
```

> 💡 **`em.getReference` vs `em.find`**: `getReference` devuelve un **proxy** sin tocar la BD; basta para asignar la FK. Si solo necesitas el id para enlazar (no leer datos del usuario), `getReference` es más eficiente. Hablaremos en detalle en el Bloque 4.

### Paso 5 — Mirar el DDL

```sql
create table users (
    id     uuid not null primary key,
    email  varchar(200) not null unique,
    nombre varchar(100) not null
)

create table comments (
    id        uuid not null primary key,
    fecha     timestamp not null,
    pizza_id  uuid not null,
    texto     varchar(1000) not null,
    user_id   uuid not null,
    constraint FK_comments_user foreign key (user_id) references users
)
```

✅ Una sola FK en `comments` (`user_id`). Ninguna tabla puente fantasma. **`pizza_id` es una columna normal**, no genera FK porque la modelamos como `@Embedded`. (Decisión consciente: lo discutimos al final.)

### Paso 6 — ¿Y si la quisiéramos bidireccional? (ejercicio dirigido)

Pregunta los alumnos: **"Necesito mostrar el perfil de un usuario con todos sus comentarios. ¿Hago la relación bidireccional?"**

**Versión bidireccional (lo que haríamos AHORA si la decisión cambiase):**

```java
// CommentJpa.java — sin cambios, sigue siendo el lado propietario
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_id")
private UserJpa autor;

// UserJpa.java — añadimos el lado INVERSO
@OneToMany(mappedBy = "autor", fetch = FetchType.LAZY)
private List<CommentJpa> comments = new ArrayList<>();
```

Cosas a observar:

- **`mappedBy = "autor"`** apunta al nombre del atributo (no de la columna) en `CommentJpa`.
- El DDL **no cambia**: sigue habiendo una sola FK en `comments`. La bidireccionalidad es 100% Java.
- Ahora `user.getComments()` lanzaría un `SELECT` a `comments WHERE user_id = ?` al accederlo.

**¿Por qué NO la haríamos bidireccional?**

1. La pregunta "comentarios de un usuario" la responde **igual de bien una query**: `SELECT c FROM CommentJpa c WHERE c.autor.id = :id`.
2. Una colección bidireccional invita a abusos: cargar todos los comentarios "porque están ahí", `toString()` recursivo, serialización JSON que entra en bucle infinito…
3. Si mañana hay 50.000 comentarios por usuario, esa colección perezosa explotará el día que alguien la materialice sin paginar.

> **Conclusión del ejercicio**: bidireccional **no es gratis**, aunque parezca cómoda. La unidireccional + query explícita es casi siempre la opción más sana.

### Mini-reto (3 min)

Mira el `CommentJpa`. La relación con `Pizza` la modelamos como `PizzaId` embebido, **no** como `@ManyToOne`. Pregunta:

1. ¿Qué pierdes con esa decisión? (Pista: integridad referencial).
2. ¿Qué ganas?
3. ¿Cómo lo arreglarías si lo quisieras como FK pero sin atravesar el agregado?

> *Respuesta esperada:*
> 1. Pierdes el `FOREIGN KEY` real en la BD. Nada impide guardar un `pizza_id` que no exista.
> 2. Ganas claridad de agregados: `Comment` no arrastra a `Pizza` al cargarse.
> 3. Puedes añadir `@JoinColumn(name = "pizza_id", insertable = false, updatable = false)` como **solo lectura**, o configurar el `@Column` con un `foreign key` constraint manual en `@Table`. Lo importante es que **el código de dominio sigue tratándolo como id**, no como objeto.

---

## 🎯 Cierre

- **Lado propietario** = el que tiene la FK. Decide los `UPDATE`.
- **`mappedBy`** = "yo soy el inverso, mira al otro lado".
- **Olvidar `mappedBy`** = tabla puente fantasma.
- **Postura por defecto**: relaciones unidireccionales. Bidireccional solo cuando el dominio realmente lo pida.

En **3.6** vemos qué pasa cuando una relación N:M necesita guardar **atributos propios** (ej.: la cantidad de cada ingrediente en una pizza), y por qué ese caso obliga a romper el `@ManyToMany` clásico.
