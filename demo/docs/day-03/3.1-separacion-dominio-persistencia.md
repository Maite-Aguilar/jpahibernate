# 3.1. Separación dominio / entidad de persistencia / mapper / repository

> **Duración estimada:** 25 min (15 min teoría + 10 min práctica)

---

## 🧠 Teoría rápida (15 min)

Hasta ahora tenemos un dominio limpio: `Pizza`, `Ingrediente`, value objects, identidad, invariantes. Todo POJO. Funciona, está testeable, no depende de nadie.

Ahora llega JPA y la tentación es obvia: **abrir `Pizza.java` y empezar a poner `@Entity`, `@Id`, `@ManyToMany`…** y listo, persistencia gratis.

**No vamos a hacer eso.** Vamos a entender por qué.

### El problema de fusionar dominio y persistencia

Si anotamos directamente el POJO de dominio con JPA:

- El dominio **pasa a depender** de `jakarta.persistence`. Lo que era un núcleo limpio ahora arrastra una librería de infraestructura.
- JPA **exige cosas que el dominio no quiere**: constructor sin argumentos, setters o reflexión sobre campos, colecciones mutables, identidad generada por la BD (`@GeneratedValue`).
- Las **invariantes** que protegen tu dominio (`Money` no puede ser negativo, una `Pizza` necesita al menos un ingrediente) **chocan** con cómo JPA rehidrata entidades desde la base de datos: JPA crea el objeto vacío y le va inyectando atributos uno a uno. No pasa por tu constructor de negocio.
- Cuando cambies de motor (de JPA a MongoDB, a un repositorio en memoria para tests, a Redis…) tendrás que tocar el dominio.

> **Regla:** el dominio no sabe que existe una base de datos. Punto.

### Las cuatro capas que vamos a separar

```
┌─────────────────────────────────────────────────────────────┐
│  DOMINIO              (POJO puro, lo que ya tenemos)        │
│  Pizza, Ingrediente, Money, PizzaId…                        │
│  Reglas de negocio. No sabe que existe JPA.                 │
└─────────────────────────────────────────────────────────────┘
                              ↑
                              │ mapea (en ambos sentidos)
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  MAPPER               (traductor)                           │
│  PizzaMapper                                                │
│  Convierte Pizza ↔ PizzaJpa                                 │
└─────────────────────────────────────────────────────────────┘
                              ↑
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  ENTIDAD DE PERSISTENCIA   (POJO con anotaciones JPA)       │
│  PizzaJpa, IngredienteJpa                                   │
│  Tiene @Entity, @Id, @ManyToMany. Es "una fila".            │
└─────────────────────────────────────────────────────────────┘
                              ↑
                              │ persiste / lee
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  REPOSITORY           (puerta a la BD)                      │
│  PizzaRepository                                            │
│  Recibe/devuelve objetos de DOMINIO (no JpaEntity)          │
│  Internamente usa el EntityManager y el Mapper              │
└─────────────────────────────────────────────────────────────┘
```

### Responsabilidades — una por capa (SRP)

| Capa | Qué hace | Qué NO hace |
|---|---|---|
| **Dominio** (`Pizza`) | Modela el negocio, valida invariantes | Saber que existe JPA o una BD |
| **Entidad JPA** (`PizzaJpa`) | Representa una fila en una tabla | Tener lógica de negocio |
| **Mapper** (`PizzaMapper`) | Traducir entre las dos | Validar reglas, decidir cuándo guardar |
| **Repository** (`PizzaRepository`) | Persistir y recuperar usando el `EntityManager` | Conocer detalles del dominio que no necesite |

> 💡 **Nota sobre nomenclatura.** Hay quien llama a la capa JPA `PizzaEntity` y a la de dominio simplemente `Pizza`. Nosotros usamos `PizzaJpa` para que el sufijo grite "esto vive en la BD" y `Pizza` para el dominio. Lo importante no es el nombre, es la **separación**.

### "¿No es esto sobreingeniería?"

Es la pregunta razonable. La respuesta: **depende del proyecto**. En un CRUD pequeño, una sola clase con `@Entity` y métodos de negocio dentro puede ser suficiente. Lo decimos sin complejos.

Pero el día que aparezca cualquiera de estas situaciones:
- Quieres testear el dominio sin levantar una BD.
- Necesitas exponer la misma entidad por REST (DTO ≠ entidad).
- Cambia el motor de persistencia.
- El equipo crece y la lógica de negocio empieza a vivir en *services* gigantes porque la entidad está "manchada".

…te alegrarás de haber separado desde el primer día. Y separar al principio cuesta una clase más; deshacer el entrelazamiento después cuesta una refactorización completa.

## 🛠 Práctica guiada (10 min)

> **Objetivo de esta sesión inicial:** preparar el esqueleto de paquetes donde iremos colocando las clases a lo largo del Bloque 3. No escribimos código todavía: solo dejamos la arquitectura visible en disco.

### Paso 1 — Estructura de paquetes

En tu proyecto Maven (el mismo del Bloque 2, que ya tiene los POJOs de dominio), crea esta estructura:

```
src/main/java/com/pizzeria/
├── domain/                       ← lo que YA tienes del Bloque 2
│   ├── pizza/
│   │   ├── Pizza.java
│   │   └── PizzaId.java
│   ├── ingrediente/
│   │   ├── Ingrediente.java
│   │   └── IngredienteId.java
│   └── shared/
│       └── Money.java
│
├── persistence/                  ← TODO esto lo crearemos hoy
│   ├── pizza/
│   │   ├── PizzaJpa.java         ← entidad JPA (3.2-3.4)
│   │   ├── PizzaMapper.java      ← traductor (3.4)
│   │   └── PizzaRepository.java  ← puerta a la BD (Bloque 4)
│   └── ingrediente/

│       ├── IngredienteMapper.java
│       └── IngredienteRepository.java
│
└── Main.java
```

### Paso 2 — Añadir las dependencias de Hibernate

En `pom.xml`, junto a lo que ya tienes:

```xml
<dependencies>
    <!-- API de JPA (Jakarta) -->
    <dependency>
        <groupId>jakarta.persistence</groupId>
        <artifactId>jakarta.persistence-api</artifactId>
        <version>3.1.0</version>
    </dependency>

    <!-- Hibernate como implementación -->
    <dependency>
        <groupId>org.hibernate.orm</groupId>
        <artifactId>hibernate-core</artifactId>
        <version>6.4.4.Final</version>
    </dependency>

    <!-- H2: base de datos en memoria para clase -->
    <dependency>
        <groupId>com.h2database</groupId>
        <artifactId>h2</artifactId>
        <version>2.2.224</version>
    </dependency>
</dependencies>
```

> 💬 Recuerda: estamos usando `jakarta.persistence`, no `javax.persistence`. El paquete cambió cuando Java EE se renombró a Jakarta EE. Si copias código antiguo y ves `import javax.persistence.*`, tradúcelo.

### Checkpoint

Antes de cerrar esta sección, verifica:

- [ ] El paquete `domain` **no importa nada** de `jakarta.persistence` ni de `com.pizzeria.persistence`.
- [ ] El paquete `persistence` sí importa cosas de `domain` (es el sentido natural: la persistencia conoce el dominio, nunca al revés).
- [ ] El proyecto compila aunque las clases estén vacías.

> **Regla mnemotécnica:** las flechas de dependencia apuntan **hacia el dominio**, nunca salen de él.
